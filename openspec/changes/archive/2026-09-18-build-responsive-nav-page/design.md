## Context

Source material is 10 static Figma HTML exports (absolute-positioned, one per breakpoint × state) covering 5 breakpoints: large-desktop (1440px), desktop (1199px), tablet (991px), mobile (768px), small-mobile (567px). All 10 files were fetched and read directly during planning; the values below (colors, icons, typography, breakpoints) are transcribed from that source, not guessed. See `proposal.md` - Why/What Changes for the behavioral summary. No code exists yet (empty repo); this design covers the whole app, not an incremental change.

Two gaps in the source material shape this design:
- No `tablet-open` frame exists — tablet (768–1439px range) is treated identically to desktop for navigation, since neither shows a sidebar or a hamburger toggle in the frames provided. Content layout still follows finer per-frame breakpoints (1199px / 768px) independently of this — the two breakpoint systems are intentionally different granularities, not a bug (see `account-content-page` spec).
- Only "Persönliche Daten" has a designed content template; the other 6 nav items have no content frame and route to the shared empty-state placeholder (see `account-content-page` spec).

Two values have no source data point at all and are documented assumptions rather than transcriptions:
- The exact pixel width where the mobile drawer's nav grid switches from 3 columns to 2 (the only reference frames are 567px, which shows 2 columns, and 768px, which shows 3 — nothing in between is specified anywhere in the material; see `--bp-small-mobile` in Decisions below).
- The exact pixel width where the content area's field style flips from stacked label-above-value back to the tablet's label/value-same-row (see the `account-content-page` spec: 991px shows same-row, 567px shows stacked-again, and there is no frame at 768px — the assumption is that this flips at the same 768/769 point as navigation mode, on the reasoning that mobile-width and small-mobile-width share the same drawer-style navigation chrome).

## Goals / Non-Goals

**Goals:**
- Reproduce the visual design pixel-faithfully at each of the 5 reference widths, while flowing smoothly between them (no fixed-width absolute positioning).
- No backend — navigation destinations are static, no data layer or API calls.
- Keep the dependency footprint minimal beyond what's needed for routing.

**Revision:** the app initially shipped with navigation selection as local `useState` in `App`, matching an original goal of "no routing library." At the user's request it was later migrated to real client-side routing (`react-router`, `createBrowserRouter`) — see the Decisions entry below. That earlier goal no longer holds; kept here (struck conceptually, not literally) so the change history stays legible rather than silently rewritten.

**Non-Goals:**
- Real authentication, real user data, or persistence — "John Smith" / static field values are hardcoded from the designs.
- Content for the 6 undesigned nav destinations beyond the shared empty state.
- Pixel-exact reproduction of intermediate widths not covered by a reference frame (e.g. 1300px) — those are interpolated using the nearest breakpoint's pattern via standard CSS media queries.
- Automated test coverage — this is a small, backend-less app; manual verification against the reference frames (`tasks.md` section 7) is the QA method for v1.

## Decisions

**No `src/shared/` folder.** `data/`, `hooks/`, `icons/`, and `styles/` stay flat under `src/`. A `src/shared/` consolidation was tried and reverted at the user's clarification: `shared/` is reserved for reusable UI *components* (a `Button`, etc.) — this app has none yet, since every component here is either page-chrome-specific (`Header`, `EmptyState`, `PersonalDataContent`) or nav-specific (`components/nav/`). Revisit if a genuinely generic, reused-in-multiple-places component shows up.

**Stack: Vite + React + TypeScript + Bootstrap (Sass, customized to match the Figma frames exactly).** No specific stack was requested beyond "React." Vite gives a zero-config dev server and build. The project shipped first as plain JavaScript (`.jsx`), then was migrated to TypeScript at the user's request (`tsc -b && vite build`; component prop interfaces, typed nav/content data, a typed `NavigationMode`/`EmptyStateVariant`). Styling shipped first as hand-written plain CSS (one stylesheet per component, BEM-ish class names, CSS custom properties for tokens) — rejecting CSS Modules only because plain CSS was sufficient at that point — then was replaced with Bootstrap 5.3 customized to match the Figma frames exactly, at the user's request (**Bootstrap adoption** below). That exact-matching was then briefly reversed in favor of Bootstrap's own stock defaults (**Bootstrap defaults reversal**), and reversed back again shortly after (**Reversal of the reversal**) once the user saw the stock-Bootstrap look rendered and asked to "return back to prev design." Every earlier "plain CSS" note in this section describes the pre-Bootstrap state; **Bootstrap defaults reversal** describes a state the app briefly passed through and no longer matches — read both historically. **Bootstrap adoption**, together with **Reversal of the reversal**, describes what's actually true now.

**Bootstrap adoption.** Bootstrap's *defaults* (576/768/992/1200/1400px breakpoints, its own theme-color palette) don't match this app's actual values, which come directly from the Figma reference frames — using Bootstrap unmodified would have meant visually drifting from the designs this whole change has been carefully matching. Instead, `src/styles/_bootstrap-custom.scss` overrides Bootstrap's Sass variables *before* importing it, so the compiled utility classes are already correct for this design:
- `$grid-breakpoints` / `$container-max-widths` → the app's actual breakpoints (600/769/1199/1440px, named `sm`/`md`/`lg`/`xl`), not Bootstrap's own. Every Bootstrap responsive utility (`d-md-none`, `row-cols-sm-3`, etc.) is therefore already scoped correctly — no separate custom-breakpoint system running alongside Bootstrap's.
- `$spacers` → extended from Bootstrap's 6-step scale (0/4/8/16/24/48px) to the design's actual 9-step scale (0/4/8/12/16/20/24/32/40/48px), so `p-*`/`gap-*`/`m-*` cover every spacing value the design uses.
- `$primary`, `$body-color`, `$body-secondary-color`, `$border-color`, `$font-family-sans-serif`, `$font-size-base` (14px), `$border-radius` (8px), `$link-color`/`$link-hover-color` (plain text, not Bootstrap's default link-blue-via-primary — nav items are links styled as text, not "link-colored") → the exact brand values.
- A handful of Bootstrap-convention extension utilities for the few things Bootstrap's utility set has no slot for at all: `.fs-2xs`…`.fs-3xl` (+ responsive `.fs-{bp}-{name}` variants, generated the same way Bootstrap generates its own responsive utilities — needed because one value, the PersonalDataContent field value's font-size, is non-monotonic across breakpoints: 15px, then 14px at the tablet tier only, then 15px again — the exact same "dip in the middle" shape as that field's `flex-column flex-md-row flex-lg-column` direction flip), `.fw-black` (900 weight, for the logo), `.text-accent-dark`/`.bg-active`/`.border-divider` (brand colors with no Bootstrap theme-color slot), `.btn-plain` (a transparent icon-button style — Bootstrap's `.btn` always implies a filled/outlined look), `.w-sidebar`/`.h-2px`/`.gap-2px`/`.py-14px` (one-off exact pixel values that don't belong in a reusable scale), `.min-w-0`/`.min-vh-svh` (missing from Bootstrap's utility set entirely), `.link-hover-underline` (hover-only underline, decoupled from color). One genuinely component-specific rule remains outside the utility system: `.pdc-field-label`'s fixed 160px width at the tablet tier only, written using Bootstrap's own `media-breakpoint-only()` mixin rather than a bespoke media query.
- Every component's markup was rebuilt on Bootstrap's grid (`.row`/`.col`/`row-cols-*` for the nav card grids and the two-column content layout) and utility classes; every per-component `.css` file (`Header.css`, `Navigation.css`, `PersonalDataContent.css`, `EmptyState.css`, `App.css`) was deleted. `App.css` in particular had drifted to being imported by `RootLayout.tsx` rather than `App.tsx` (a leftover from the routing migration) — folding its rules into `RootLayout.tsx`'s own utility classes resolved that naming/ownership mismatch as a side effect of the rewrite.
- Two regressions were caught by re-running the full breakpoint sweep after the rewrite (not assumed away): the content field's label was wrongly center-aligned at the desktop tier (`align-items-md-center` was never reverted to `flex-start` at `lg`, unlike the other properties in that same non-monotonic flip — fixed with `align-items-lg-start`), and "Beschäftigungsdaten" (one long unbreakable German compound word) overflowed its ~130px column at 320px width because the old CSS's `overflow-wrap: break-word` had no Bootstrap-utility equivalent added in the rewrite — fixed with Bootstrap's `.text-break`.

**Bootstrap defaults reversal.** The user asked why `_bootstrap-custom.scss` was needed; the answer (matching the Figma frames exactly) prompted the question "why not just use Bootstrap's own defaults instead?" — confirmed explicitly (not assumed from a one-word "do it": the scope was spelled out and re-confirmed before touching anything, given how large a reversal this is) as: drop the Figma-exact breakpoints/colors/spacing, accept Bootstrap's own stock values, accept the resulting visual drift from the Figma reference frames. What actually changed in `_bootstrap-custom.scss`:
- `$grid-breakpoints` / `$container-max-widths` overrides **removed** — Bootstrap's own 576/768/992/1200/1400px tiers apply now, not the Figma-derived 600/769/1199/1440px.
- `$primary`, `$body-color`, `$body-secondary-color`, `$border-color`, `$font-family-sans-serif`, `$font-size-base`, `$border-radius` overrides **removed** — Bootstrap's own default blue theme, system font, and 6px radius apply now, not the brand green/Inter/8px.
- The `:root` custom properties (`--color-accent-dark`, `--color-active-bg`) **no longer hardcode the old brand hex values** — they're derived from Bootstrap's own (now-default) `$primary` via Bootstrap's own `shade-color()`/`tint-color()` functions, so the active-nav-item state stays a coherent shade of whatever `$primary` actually is, rather than leaving a stray brand-green behind after everything else went blue. `--color-divider` maps to Bootstrap's own `$gray-200`.

What deliberately did **not** revert, because it isn't "Figma fidelity" and reverting it would have broken rendering rather than made it look more like stock Bootstrap:
- The extended `$spacers` scale (steps 6–9, i.e. 24/32/40/48px) — components reference `gap-6`..`gap-9`/`p-6`..`p-9` throughout; Bootstrap's default scale stops at step 5. Reverting this would have silently dropped padding/gaps in multiple places rather than "looked generic."
- `$link-color`/`$link-hover-color` staying pinned to `$body-color` (now Bootstrap's own default body color, not the old brand hex) — without this, every inactive nav item renders as a blue hyperlink instead of plain nav text, since nothing else in `NavItem` sets an explicit color for the inactive state. This is a structural choice about what a nav item looks like, independent of which palette is active.
- Every extension utility class below the `@import` (`.fs-*`, `.fw-black`, `.gap-2px`, `.py-14px`, `.text-accent-dark`, `.text-border-color`, `.bg-active`, `.border-divider`, `.btn-plain`, `.w-sidebar`, `.h-2px`, `.min-w-0`, `.min-vh-svh`, `.link-hover-underline`, `.pdc-field-label`) — components reference these by class name; removing them breaks rendering, it doesn't make the app look more like default Bootstrap.

Two things had to change alongside the SCSS file to keep the app internally consistent, not just cosmetically different:
- `useNavigationMode.ts`'s sidebar/inline/drawer breakpoints were hardcoded JS media-query strings (`769px`/`1440px`), entirely independent of the SCSS `$grid-breakpoints` map. Left alone, this would have desynced nav *chrome* (still switching at the old Figma-exact widths) from CSS-driven content *layout* (now switching at Bootstrap's own tiers) — e.g. between 992–1199px, content styling would already be at the new "lg" tier while nav chrome was still "inline" mode. Updated to Bootstrap's own `md`/`xl` (768px/1200px) so both switch together.
- Overriding `$link-color: $body-color` before Bootstrap's real import references `$body-color` before it's defined (Bootstrap's own default only exists once its `_variables.scss` partial has run). Fixed with the standard Bootstrap customization pattern: `@import 'bootstrap/scss/functions'` and `@import 'bootstrap/scss/variables'` first (definitions only, no CSS output) so `$body-color` — and `shade-color()`/`tint-color()`, needed for the `:root` block above — are available before the override and the real `@import 'bootstrap/scss/bootstrap'` that follows.

Every previously-documented rationale above this point for *why* 769 (not 768) or 1199 (not 1200) or the specific brand hex values — is now historical: it explains a design this app matched at the time, not the app as it exists after this reversal.

**Reversal of the reversal.** This didn't stick — the user asked to "return back to prev design" shortly after seeing it rendered (Bootstrap's default blue in place of the brand green was the trigger). `_bootstrap-custom.scss`'s breakpoints/colors/font/radius overrides and the `:root` block were restored verbatim to the **Bootstrap adoption** version above (Figma-exact 600/769/1199/1440px, `#92C81C` primary, Inter, 8px radius, hardcoded `--color-accent-dark`/`--color-divider`/`--color-active-bg`), and `useNavigationMode.ts` went back to 769px/1440px. Two fixes made *during* the reversal were kept rather than rolled back, since they're correct regardless of which color scheme is active, not Figma-vs-Bootstrap-defaults concerns:
- `.btn-plain { color: inherit; }` — the header toggle icon's `currentColor` needs this regardless of what the ambient text color actually is (see **Bootstrap adoption**'s icon-refactor note above); without it the icon is black under either color scheme.
- `$_font-sizes`'s `'base'` entry referencing `$font-size-base` instead of a hardcoded `0.875rem` — cosmetically identical here since `$font-size-base` is explicitly `0.875rem` again, but correct either way rather than a value that silently drifts from the variable it's meant to track.

The `functions`/`variables` preload that the reversal needed (to reference `$body-color` and `shade-color()`/`tint-color()` before Bootstrap's real import) is gone along with the rest of that version — this file no longer needs it, since `$body-color` is defined locally again before `$link-color` references it, and nothing here calls Bootstrap's color functions anymore.

So: as of this point, the app is back to matching the Figma reference frames exactly, as described in **Bootstrap adoption** above. The **Bootstrap defaults reversal** section above this one is now itself historical — it describes a state the app passed through, not its current one.

**Readability cleanup.** Asked directly "do I have clean, well-structured UI," the honest answer had two real caveats, not just style opinions: `PersonalDataContent.tsx` had lines with 10+ Bootstrap utility classes on one `className` (genuinely harder to scan than the old semantic BEM classes it replaced), `_bootstrap-custom.scss` had grown to 213 lines with five distinct concerns in one file, and `components/icons/` was the one component folder still lowercase against `Header`/`EmptyState`/`Navigation`/`PersonalDataContent`'s PascalCase. All three fixed without touching the underlying Bootstrap-utility decision:
- Every component with a non-trivial `className` string now assigns it to a named module-level `const` above the component (e.g. `FIELD_ROW`, `STAT_BLOCK`, `LAYOUT_WRAPPER`) — restores the "one name explains this element" property the old CSS classes had, without reintroducing custom CSS. Verified first that none of the 14 custom utility classes or 8 `fs-*` scale steps were dead code (all confirmed used) before touching anything, so this was purely a JSX-readability pass, not a cleanup that also happened to change behavior.
- `_bootstrap-custom.scss` split into `_variables.scss` (the Bootstrap variable overrides — "what we tell Bootstrap to be") and `_utilities.scss` (the `:root` tokens, `fs-*` generator, and all extension classes — "what we add on top"), with `_bootstrap-custom.scss` itself reduced to a 3-line orchestrator (`@import` variables, then Bootstrap, then utilities). Compiled CSS output is byte-identical (verified via build output size) — this is purely a file-organization change.
- `components/icons/` → `components/Icons/`, with every import path updated to match. Hit one real, non-obvious snag doing this: after the rename, some import specifiers still used the old lowercase `'../icons'` while others used the new `'../Icons'` pointing at the same physical directory — TypeScript treats that as a same-file-different-casing conflict and errors, even on a case-insensitive filesystem where both paths resolve to the same file on disk. Fixed by making every import consistently use the new casing.

**Project scaffold caveat.** `npm create vite@latest .` run directly in the repo root will refuse or prompt because `openspec/` and `.claude/` already exist there. Scaffold into a temp directory instead and copy `src/`, `index.html`, and config files into the root afterward, leaving `openspec/` and `.claude/` untouched.

**Breakpoints as CSS custom properties, mirrored in JS via `matchMedia`.** Correction found during implementation: the reference "mobile" frame is exactly 768px wide and uses the drawer/hamburger pattern, so 768px must resolve to drawer mode, not inline mode — the split is 768/769, not the more common 767/768. All specs and the boundary below were fixed to match.
- `--bp-large-desktop: 1440px` (sidebar mode, `min-width`)
- `--bp-desktop: 769px` (inline-grid mode, `min-width`, up to large-desktop)
- `--bp-desktop` and below (≤768px): drawer mode
- `--bp-small-mobile: 600px` — a documented assumption, not sourced from a reference frame (see Context above). This is the threshold within drawer mode where the nav grid drops from 3 columns to 2. Chosen as the midpoint between the two reference frames (567px shows 2 columns, 768px shows 3); revisit if a designer specifies an exact value. Consumed directly in CSS (`grid-template-columns`), not by the navigation-mode hook below, since it only affects column count within drawer mode, not the mode itself.

A single `useNavigationMode()` hook wraps `matchMedia` listeners for `--bp-desktop` and `--bp-large-desktop` and returns `'sidebar' | 'inline' | 'drawer'`, so nav components branch on one value instead of re-deriving breakpoints in multiple places.

Cross-checking the sidebar (`large-desktop-content.html`), the inline grid (`desktop-open.html`), and the drawer grid (`mobile-open.html`, `small-mobile-open.html`) gives a fully confirmed mapping for all 7 items:

| Persönliche Daten | user | user |

Two things worth calling out from that cross-check:
- In `mobile-open.html` and `small-mobile-open.html`, the "Persönliche Daten" and "E-Mail ändern" cards' SVG path data is pixel-identical (just scaled) to the header's own close icon — an X inside a circle — rather than the user/mail icons those items use everywhere else, including the same drawer frame's own layer-naming (`Icon-user profile card`, `Icon-envelope mail edit`). This reads as a Figma placeholder that was never swapped to the real icon, not an intentional third icon. The implementation uses the semantically correct icon (`user`, `mail`) in the drawer grid rather than reproducing the placeholder, since matching the file's own evident intent takes priority over an apparent authoring slip.
- "Kunden werben" genuinely differs by tier: `gift` in the sidebar and inline-grid frames, `handshake` in both drawer-grid frames. Unlike the case above, this is consistent across both drawer frames (not a one-off), so it's treated as an intentional per-tier choice and reproduced as-is: `IconGift` in sidebar/inline mode, `IconHandshake` in drawer mode.

**Icons folder restructured at the user's request: `src/icons/index.tsx` → `src/components/icons/` (one file per icon + a shared `Icon.tsx` primitive + a barrel `index.ts`), `stroke` normalized to `currentColor` everywhere, `size` made optional.** The single-file version had a real inconsistency worth fixing along the way: 4 of the 13 icons (`IconMenu`, `IconXCircle`, `IconLockKeyholeLarge`, `IconShieldCheck`) hardcoded their stroke color directly on the `<path>` rather than accepting it as a prop, while the other 9 did — an artifact of how they were transcribed one at a time during the original build, not a deliberate distinction. All 13 now uniformly destructure `{ stroke = 'currentColor', ...props }`.

`currentColor` is not a value-preserving no-op for two of them: `EmptyState`'s lock (`#777777`) and shield (`#E9EAEA`) icons are deliberately lighter than the app's default body text color and different from each other, so leaving their call sites without an explicit color would have silently rendered them as dark body-text color instead. Fixed by giving `EmptyState` an explicit `className` per variant (`.text-body-secondary`, an existing exact match for `#777777`; `.text-border-color`, a new one-line extension in `_bootstrap-custom.scss` for `var(--bs-border-color)` = `#E9EAEA`, following the same pattern as `.text-accent-dark`).

The visual verification pass caught a second, unrelated bug this surfaced: the header's hamburger/close toggle icon rendered pure black instead of `#333333`, because `<button>` elements don't inherit `color` from their ancestors by default (the browser UA stylesheet sets it to the `buttontext` keyword) — Bootstrap's own `.btn` class resets this, but `.btn-plain` (the icon-button extension added for this toggle) deliberately opts out of `.btn` entirely and hadn't accounted for it. Fixed with one line, `color: inherit;`, on `.btn-plain`. Both fixes were confirmed with computed-style checks (not just a visual glance) against the exact original hex values before and after.

Icon components needed: `IconMenu`, `IconXCircle` (header hamburger/close toggle, 24px viewBox), `IconBanknote`, `IconUpload`, `IconUser`, `IconMail`, `IconLockKeyhole`, `IconGift`, `IconHandshake`, `IconLogOut` (nav items, 20px viewBox), `IconMars` (14px viewBox, "Anrede" gender glyph in content), and `IconLockKeyholeLarge` / `IconShieldCheck` (the two `EmptyState` variants, 48px viewBox).

Correction found during implementation: an earlier draft of this section stated `IconLockKeyhole` was reserved for `EmptyState` and not shared with nav items — that's wrong. "Kennwort ändern" genuinely uses the lock-keyhole icon (confirmed above), and the large-desktop empty state's lock icon is the same shape at 48px. The Figma export's nav-sized (20px viewBox, stroke-width 2) and empty-state-sized (48px viewBox, stroke-width 2) path data are a uniform 2.4× scale of each other in coordinates, but stroke-width is fixed in absolute terms in both, not scaled — so naively rendering one component at two sizes via CSS would make the stroke visibly too thick or thin at one of them. `IconLockKeyhole` (20px) and `IconLockKeyholeLarge` (48px) are therefore two separate components using their own native path/viewBox/stroke-width from the export, not one component with a `size` prop.

**Typography tokens, sourced from the export.** Alongside the color/spacing/radius tokens, define font-size and font-weight custom properties matching the values actually used in the designs (not placeholders):
- Logo wordmark: 26px / weight 900
- Tagline ("Einfach 60 Tage Geld leihen"): 11px / weight 500
- Section headings ("Persönliche Daten", "Navigation", etc.) and user name / "Identifiziert": 16–18px / weight 700 (18px for section/nav headings, 16px for the user-identity values)
- Nav item label: 14px / weight 500, weight 700 when active
- Field label (e.g. "Anrede"): 13px / weight 400 at desktop, large-desktop, and tablet widths; 12px / weight 400 at mobile/small-mobile widths
- Field value (e.g. "Herr"): 15px / weight 600 at desktop, large-desktop, and mobile/small-mobile widths; 14px / weight 600 at tablet width only
- "Hallo," / status caption text: 13px / weight 400 at desktop widths, 12px / weight 400 at mobile width
- Empty-state message: 14px / weight 400

**Navigation is real client-side routing (`react-router`), not local component state.** Originally `activeItemId`/`drawerOpen` were both `useState` in `App`, with a hand-rolled "how does selection survive a resize" mechanism. At the user's request this was replaced with `createBrowserRouter`: each nav item is a real `<Link to={`/${item.id}`}>` with a genuine href, the selected destination is the URL's `:itemId` param (read via `useParams`), and only `drawerOpen` (a transient UI toggle, not a "place" in the app) remains local `useState`. This is a strict behavioral upgrade over the old approach: selection now survives a full page reload and browser back/forward, not just a viewport resize, and every destination is bookmarkable/shareable/right-clickable — all for free from adopting `<Link>`/`<Route>` instead of `onClick`/`useState`. Structure:
- `src/routes/router.tsx` — the `createBrowserRouter` config: `/` is a pathless layout route (`RootLayout`) with two children, an `index` route (`IndexRoute`, path `/`) and a `:itemId` route (`DestinationRoute`).
- `src/routes/RootLayout.tsx` — what `App.tsx` used to be: picks the sidebar/inline/drawer chrome by `useNavigationMode()`, reads `activeItemId` from `useParams()`, and renders `<Outlet context={mode} />` where the content area used to go. `App.tsx` itself is now just `<RouterProvider router={router} />`.
- `src/routes/IndexRoute.tsx` / `DestinationRoute.tsx` — the two possible contents of that `<Outlet>`: the empty-state placeholder, or `PersonalDataContent` when `itemId` matches `CONTENT_DESTINATION_ID`. Both read `mode` back out via `useOutletContext<NavigationMode>()` to pick the lock vs. shield `EmptyState` variant.
- `NavItem` (in `components/nav/`) now renders a `<Link>`, not a `<button onClick>`; its `onSelect` prop became `onNavigate?: () => void`, used only by `DrawerNav` to close the drawer as a side effect of the `Link`'s own `onClick` — `SidebarNav`/`InlineNav` need no side effect at all, since navigating is what `Link` already does.

**Inline-grid mode's "back to navigation" control.** The Figma frames never show inline-grid content and the nav grid simultaneously, and no back affordance is drawn — but one is required for the content view to be reachable back to navigation without a full-page reload. Implemented as a `<Link to="/">` ("← Navigation") at the top of the content area, visible only in inline mode. Alternative considered: make the section heading itself clickable — rejected as less discoverable than an explicit link.

**Undesigned destinations in inline-grid mode reuse the large-desktop empty state.** Inline-grid mode's default (nothing selected) state is the navigation grid itself, not a placeholder — so it has no empty-state visual of its own for the case where a user selects one of the 6 undesigned items. Rather than inventing a third placeholder variant, that case reuses the large-desktop lock-icon variant verbatim (see `account-content-page` spec).

**Content field data as a static local array.** The `Persönliche Daten` fields (label + value pairs, grouped by section) are defined as a plain JS array/object in the component, not fetched — there is no backend in scope.

## Risks / Trade-offs

- [No design exists for the 6 non-personal-data destinations] → Mitigation: they render the same empty-state component used for "nothing selected"; documented in the spec and proposal so it's a visible, intentional gap rather than a silent omission.
- [Tablet inferred, not designed, for navigation chrome] → Mitigation: reuses the desktop inline-grid pattern exactly (same code path — 768–1439px covers both for navigation only; content layout still differentiates at 1199px), so behavior is at least internally consistent even if not designer-verified.
- [`--bp-small-mobile: 600px` is an assumption, not a sourced value] → Mitigation: documented here and in the proposal; easy to adjust in one place (a single CSS custom property) if a designer specifies an exact value later.
- [The content area's stacked/same-row field-style flip at 768/769px is inferred, not sourced — see Context above] → Mitigation: reuses the navigation-mode breakpoint rather than inventing a fourth breakpoint system, so it's at least consistent with a boundary that does have some justification.
- [`matchMedia`-driven mode switching could cause a flash of the wrong layout on resize in dev tools] → Mitigation: mode is derived synchronously from `window.matchMedia(...).matches` on first render (no `useEffect`-only initialization), so the initial paint matches the actual viewport without a corrective re-render.

**Tests and README added, checked against an explicit checklist.** The user ran this app through a general "clean, production-ready UI" checklist item by item. Two items were genuine oversights with nothing blocking them, fixed here: zero automated tests existed (`vitest` + `@testing-library/react` + `jsdom` added; 19 tests across 5 files — `useNavigationMode`'s breakpoint boundaries, `NavItem`'s active-state and icon-swap logic, `EmptyState`'s per-variant copy/color, `PersonalDataContent`'s data-driven field rendering, and a `RootLayout` integration test that renders the real route tree via `createMemoryRouter` and clicks through it), and `README.md` was still the unedited stock Vite template from the original scaffold. Two other checklist items — a service/API layer, forms with validation — were deliberately **not** added: this app has no backend and no editable data by design (see Goals/Non-Goals above), so building either would be fabricating scope the app doesn't have, not fixing a gap. Flagged to the user as such rather than added silently.
